# 快速参考 — Omni-One 每日结算（一页速查表）

> 把这页打印出来，贴在打包台旁边的墙上。
> 一条命令跑完店铺的早晨：利润、补货、回复、堵漏。
> 每个数字都引用 `file:line`。无引用，不行动。
> 来源：`docs/QUICKSTART.md`、`docs/API.md`、`docs/CLI.md`、
> `docs/DEPLOYMENT.md`、`docs/ROADMAP.md`、`docs/DAILY_CLOSE.md`、
> `docs/handbook/01-morning-routine.md`、`docs/handbook/05-incidents.md`、
> `docs/SCENARIOS.md`、`src/omni_one/packs/seller_scenarios.py`。

```bash
omni-one close --folder ~/my_shop --out ./close_today
# -> close.json + close.csv + reorder.csv + replies.txt + po.txt
```

标题行示例（你必须读的唯一一行）：

```
Profit $169.09 (61.7%) · $102.75 at risk in 3 angry messages · 1 reorder(s) TODAY · 0 leak(s) to plug
```

## 1. 5 分钟仪式（检查清单）

把这份清单过塑。计时开始，不要在后台面板里闲逛。

- [ ] **0:00–0:30 — 跑结账。**
  ```bash
  omni-one close --folder ~/my_shop --out ./close_today
  ```
  大声读出标题行。如果报错，见 §12 故障排查。

- [ ] **0:30–2:00 — 先回消息。**
  打开 `replies.txt`。复制粘贴草稿 #1，个性化改一句话，发送。
  趁烧水重复。
  规则：**P0（退款 / 未到 / 破损）2 小时内必回，无例外。**
  见 `docs/handbook/03-reply-playbook.md`。

- [ ] **2:00–3:30 — 补货。**
  打开 `reorder.csv`。凡是 `ORDER TODAY` → 今天就把 `po.txt` 草稿发出去。
  凡是 `this week` → 记到日程。
  见 `docs/handbook/02-supplier-playbook.md`。

- [ ] **3:30–4:30 — 堵一个漏。**
  如果 `close.csv` 里的 `money_leaks` 非空，做最便宜的修复：
  通常是某 SKU 涨价 $1，或把某 SKU 移出高费率渠道。
  记一行日志。

- [ ] **4:30–5:00 — 归档。**
  把当天的导出移到店铺文件夹。
  给台账加一行（见 `docs/handbook/04-accountant-pack.md`）。

每日过塑卡（精简版）：

- [ ] 跑完结账，读完标题行
- [ ] 所有 P0 回复 < 2h 发完
- [ ] `ORDER TODAY` 的 PO 发完
- [ ] 堵了一个漏
- [ ] 文件已归档

每周（周五，20 分钟）：

- [ ] 7 天结账对平，GMV 与渠道后台 ±2%
- [ ] 催供应商 ETA（下单 > 7 天无单号的）
- [ ] 列出滞销（0 销量 + 5+ 件 → 清仓草稿）
- [ ] 对照费率变化检查价格
- [ ] 备份：把 `~/my_shop` 拷到 U 盘 / 第二台电脑

每月（第一个周一，1 小时）：

- [ ] 当月 `close.csv` → 会计交接包
- [ ] 更新供应商记分卡（价格、ETA、次品率）
- [ ] 最差单品决策：下架、打包还是清仓
- [ ] 毛利底线：综合真实毛利 ≥ 10%？

## 5. 阈值表（按店铺可调，代码：`src/omni_one/packs/seller_scenarios.py`）

| 键 | 值 | 触发条件 | 动作 |
|---|---|---|---|
| 断货 | 5d | 7 天销量速度 vs 现有库存 < 5 天 | `reorderProduct` |
| 备货覆盖 | 14d | `reorder_qty = ceil(velocity×14 − on_hand)` | 按 14 天备货下单 |
| 手续费偏高 | 12% | 手续费 / GMV × 100 ≥ 12% | `reviewPricing` |
| 运费亏损 | 20% | 运费 / GMV × 100 ≥ 20%（单订单） | `adjustShipping` |
| 毛利底线 | 10% | 净毛利 < 10% | `reviewPricing` |
| DM 积压 | 3 | ≥ 3 条未处理 DM | `triageDMs` |
| 价格不一致 | 5% | 同 SKU 跨渠道 ±5% | `alignPrice` |

结算包用的紧急度：

| `days_left` | 标签 | 做法 |
|---|---|---|
| < 3d | `ORDER TODAY` | 今天发 PO |
| 3–5d | `this week` | 记日程 + 确认 ETA |
| > 5d | 健康 | 明天再看 |

公式（确定性，无 LLM 参与数字）：

| 指标 | 公式 | 黄金演示 |
|---|---|---|
| 真实利润 | GMV − 手续费 − 运费 − COGS | GMV $274.00 → 利润 $169.09（61.7%） |
| 客单价 AOV | GMV / 订单数 | 演示约 $34.25 |
| 风险金额 | 未回复投诉 × AOV | 3 × $34.25 ≈ $102.75 |
| 日均销量 | 7 天销量 / 7 | Tote：6 / 7 ≈ 0.857/天 |
| 剩余天数 | 现有库存 / 销量速度 | Tote：2 / 0.857 ≈ 2.3d → ORDER TODAY |
| 补货量 | ceil(速度 × 14 − 库存) | Tote：ceil(12 − 2) = x10 |
| 费率 % | 手续费 / GMV × 100 | ≥ 12% → 漏损 |
| 运费 % | 运费 / GMV × 100（单订单） | ≥ 20% → 漏损 |
| 净毛利 | (GMV − 手续费 − 运费) / GMV × 100（速算） | < 10% → PROFIT_DIP |

滞销：库存 ≥ 5 且 7 天 0 销量 → `markDownProduct`（打包/清仓）。
COGS 飙升：供应商金额 / GMV > 1.5× → `renegotiateSupplier`。
Listing 缺口：销量 ≥ 2 且 0 评价 → `requestReview`（求 UGC）。

## 6. 12 个场景（每个 60 秒演示）

运行：`POST /api/v1/seller/scenarios/run {"demo":true}`。
验证：`PYTHONPATH=src python -m pytest tests/unit/test_seller_scenarios.py -q`。

| # | 场景 | 严重度 | 触发 | 证据 | 工作台动作 |
|---|---|---|---|---|---|
| 1 | STOCKOUT_RISK | `high` | 库存 < 5d。演示：Tote 剩 2 件，6/7d = 2.3d | `[inventory.csv:2] Tote 2 left` | `reorderProduct` |
| 2 | DEAD_STOCK | `medium` | 库存 ≥ 5，7d 0 销量 → 清仓 | `[inventory.csv]` | `markDownProduct` |
| 3 | UNANSWERED_COMPLAINT | `critical` | 负面 DM 且后面无店铺回复 | `[instagram_dm.txt:1] Alice…` | `messageCustomer` |
| 4 | REFUND_RISK | `critical` | 退款/退货/未到语言 | `[dm:1] …` | `messageCustomer` 2h SLA |
| 5 | REVIEW_CRISIS | `high` | 1–2 星或破损/损坏 | `[reviews.csv:3] …` | `replyReview` |
| 6 | DM_BACKLOG | `medium` | ≥ 3 条未处理 DM | `[dm:1]` 最早一条 | `triageDMs` |
| 7 | FEE_CREEP | `medium` | 手续费/GMV ≥ 12% | `[orders] fees $…` | `reviewPricing` |
| 8 | SHIPPING_LOSS | `medium` | 运费/GMV ≥ 20%（单订单） | `[shopify:5] ship $…` | `adjustShipping` |
| 9 | PROFIT_DIP | `high` | 净毛利 < 10% | `[orders] net $…` | `reviewPricing` |
| 10 | SUPPLIER_COGS_SPIKE | `medium` | 供应商金额 / GMV > 1.5× | `[supplier_invoice…]` | `renegotiateSupplier` |
| 11 | PRICE_MISMATCH | `low` | 同 SKU 在 Shopify/Etsy 差 ±5% | `[orders] {shopify:28, etsy:30}` | `alignPrice` |
| 12 | LISTING_GAP | `low` | 销量 ≥ 2 且 0 评价 → 求 UGC | `[orders] sold N` | `requestReview` |

严重度排序：`critical` → `high` → `medium` → `low`。
ID 稳定（类型+键的 `_sid` 哈希）→ 幂等：同样事件 → 同样决策。
`scenarios_to_workshop()` 落到 `Product:*`（无幻觉）并按 `stable_id` upsert。
技术：`packs/seller_scenarios.py:1` 单遍 `_ctx()` O(n)，纯函数。

## 7. 引用格式（唯一规则）

> **无引用，不行动。** 结算拒绝编造任务。
> 如果它让你补货，它会给出 `[inventory.csv:2]`。
> 如果它让你回消息，它会给出 `[instagram_dm.txt:4]`。

| 模式 | 示例 | 含义 |
|---|---|---|
| `[inventory.csv:2]` | `Reorder Tote — 2.3d left [inventory.csv:2]` | 库存文件第 2 行 |
| `[instagram_dm.txt:4]` | `Unanswered complaint [instagram_dm.txt:4]` | DM 导出第 4 行 |
| `[reviews.csv:3]` | `Bad review [reviews.csv:3]` | 评价第 3 行 |
| `[shopify_orders.csv:5]` | `Shipping loss [shopify_orders.csv:5]` | 订单第 5 行 |
| `[supplier_invoice.jpg:1]` | `COGS $… [supplier_invoice.jpg:1]` | OCR 第 1 行 + 侧车 `.jpg.txt` |

规则：

- 标题行每个数字在 `close.json` 里都有引用链。
- 如果数字没有引用，不要信——去修源文件，而不是修表格。
- 匹配是模糊的（`Tote` ≈ `Tote Bag Handmade`），但完全同名最保险——改成一致即可。
- 去重按内容哈希：完全相同的内容（`.jpg` + `.jpg.txt` + `.txt`）只算一次。看简报里的 `files_ingested` vs `files_seen`。
- `file:line` 字符串永不翻译——ES/ZH 文档里保持原文。

## 8. 输入文件（把你的混乱原样丢进来）

解析器自动识别，无需改名。订单文件命名为 `shopify_*`、`etsy_*`、`amazon_*` 可提高渠道识别率。

| 文件 | 内容 | 说明 |
|---|---|---|
| `shopify_orders.csv` / `etsy_settlement.csv` / `amazon_*.csv` | 订单（任意表头） | Sniffer 处理 `;` 分隔 + BOM（`UTF-8-SIG`） |
| `inventory.csv` | 库存 + 保留 `supplier` 列 | 产品名须与订单一致 |
| `reviews.csv` | 带星级的评价 | 1–2★ 或损坏词触发危机 |
| `instagram_dm.txt` / `tiktok_dm.json` | 文本/JSON 的 DM | 截图解析不了——粘贴文本 |
| `supplier_invoice.jpg/png/pdf/txt` | OCR 或 CSV 的 COGS | Tesseract OCR + 侧车 `.jpg.txt` 按哈希去重 |
| `examples/my_shop_template/*.csv` | 空白模板 | 拷到店铺文件夹填空即可 |

第 1 天文件夹配方：

```bash
mkdir -p ~/my_shop
# 放入：订单导出 + inventory.csv + 评价导出 + DM 导出 + 供应商发票
omni-one briefing --folder ~/my_shop   # 确认 GMV 与渠道后台差异 5% 以内
omni-one close --folder ~/my_shop --out ./close_day1
```

## 9. 输出文件（你本来就在用的产物）

| 文件 | 给谁 | 内容 |
|---|---|---|
| `close.json` | API / MCP / 自动化 | 全部：标题、kpis+money_at_risk、do_today、reorder_sheet、reply_queue+drafts、leaks、listing_fixes、po_draft |
| `close.csv` | 会计 / 表格 | KPI + 行动 + 漏损（A 节：fees/shipping/cogs；`money_leaks`） |
| `reorder.csv` | 供应商 | 产品、库存、剩余天数、14 天量、供应商、引用 |
| `replies.txt` | 你（复制粘贴） | 草稿 + PO 邮件合一的可打印文件 |
| `po.txt` | 供应商 | 原样发送：`Subject: Reorder — Acme Textiles: Tote x10 (2 left, 2.3d supply) [inventory.csv:2]` |
| `briefing.csv` | 表格 | 经 `omni-one export` / `GET /api/v1/seller/export.csv` 导出 |

早晨映射（出自 `docs/DAILY_CLOSE.md`）：

| 分钟 | 你做 | 结算给你 |
|---|---|---|
| 0–1 | 读标题行 | `Profit $169.09 (61.7%) · $102.75 at risk in 3 angry messages · 1 reorder TODAY · 0 leaks` |
| 1–3 | 复制粘贴回复 | `replies.txt`：3 条草稿，带姓名、问题、订单引用 |
| 3–4 | 发 PO | `po.txt`：带引用的补货单 |
| 4–5 | 归档 + 改一个 listing | `close.csv` → 会计；从 `listing_fixes` 改 1 个 |

习惯循环：

- 第 1 天：放下文件夹 → 拿到结算包 → 省下一笔退款 ≈ 全年回本（它是 $0）。
- 第 7 天：供应商目录 + 销量速度学到 → 补货量更聪明，PO 一键。
- 第 30 天：`money_at_risk → $0` 连击 + 毛利趋势 → 结算变成店铺的损益表。

## 10. 事件严重度表 + 运行手册（第一个小时决定胜负）

### 严重度刻度（所有手册通用）

| Sev | 含义 | 响应时间 | 谁 |
|---|---|---|---|
| S1 紧急 | 正在亏钱（拒付、爆款断货、账号警告） | < 1h | 你，放下一切 |
| S2 高 | 几天内会亏钱（只剩 2 天库存、1 星在涨浏览、费率跳涨） | < 4h | 你，今天 |
| S3 中 | 毛利侵蚀 / 慢失血 | 本周 | 计划时段 |
| S4 低 | 观察，无需行动 | 记录 + 复查 | 下次结账 |

全爆时排序：断货（收入停）→ 1 星（声誉）→ 费率（毛利）。大声说出来。

### 运行手册 A — 断货

发现：`reorder.csv` 显示爆款 `ORDER TODAY`（`days_left` < 3），
或简报告警 `Stockout risk: X only N left, D days supply` + `[inventory.csv:N]`。

| 信号 | Sev |
|---|---|
| top-3 的 `days_left` < 1 | S1 |
| 任一 SKU `days_left` 1–3 | S2 |
| `days_left` 3–5 | S3 |
| 无库存文件 / 产品未匹配 | S2（睁眼瞎 = 危险） |

行动（S1/S2，30 分钟盒）：上架确认 `on_hand` → 发 `po.txt`（要单号 + 分批发货）
→ 保护 listing（涨价 10–15% / 限量 / 暂停广告，胜过超卖）
→ 先安抚等待买家（模板 19）→ 若 ETA > `days_left`，今天就给备用供应商下试单。

### 运行手册 B — 1 星评价

发现：`at_risk` 跳涨、`reply_queue` 多一行 `review`，或 `REVIEW_CRISIS` + `[reviews.csv:N]`。

| 信号 | Sev |
|---|---|
| 爆款 1★ + 安全/过敏/拒付 | S1 |
| 1–2★ 有损坏/延迟细节，< 24h | S2 |
| 1–2★ 模糊、较旧 | S3 |
| 3★ 建设性 | S4 |

行动（S1/S2，45 分钟盒）：读 `[reviews.csv:line]` → 公开回一次（模板 08，绝不争辩、不公开谈退款）
→ 私信二选一（模板 05/06，S1 先给退款）
→ 今天就为下一个买家修原因 → 记录：日期、SKU、说法、成本、修复。

### 运行手册 C — 费率飙升 / 毛利崩盘

发现：`money_leaks` 显示 `fee_creep`（费率 ≥ GMV 的 12%），或毛利周环比掉 > 5 个点，或渠道宣布涨费。

| 信号 | Sev |
|---|---|
| 综合毛利 < 0% | S1 — 今天停付费流量 + 暂停最差 SKU |
| 综合毛利 0–10% 持续 2+ 周 | S2 |
| 单渠道宣布涨费 | S3 |
| 运费漂移（+$1/单趋势） | S3 |

行动（S1/S2，60 分钟盒）：在 `close.csv` A 节确认（费率 vs 运费 vs cogs——主人不同）
→ 费率：调价（`fee_delta / (1 − fee_rate)`；$28 上 2 个点 ≈ +$1）或把接下来 10 单换渠道
→ 运费：重称打包后重量，换小箱
→ COGS：无预告 +5% = 48h 内发邮件；top-3 的 COGS > 售价 45% = 调价 + 谈判并行
→ 干掉/拯救最差单品：清仓 / 打包 / 下架。

跨事件规则：一次只处理一个 · 边做边贴引用
· 全部限时（2h 的良好胜过明天的完美）
· 复盘最多 5 行 · 知道何时不是事件（S4、±2 点波动、缓慢的周二）。

## 11. 费率表 + 毛利数学

| 渠道 | 费率 | $28 示例 | 说明 |
|---|---|---|---|
| Etsy | ≈ 6.5% + $0.20 | ≈ $2.02 | 固定部分伤小单 |
| Shopify | ≈ 2.9% + $0.30 | ≈ $1.11 | 自营量大最便宜 |
| Amazon | ≈ 15% | ≈ $4.20 | 只放高毛利 SKU |
| 综合告警 | ≥ GMV 的 12% | — | 触发 `FEE_CREEP`，检查定价/渠道组合 |

经验法则：

- 需要涨价 ≈ `fee_delta / (1 − fee_rate)`。
- 综合费率 > GMV 的 12%，挑一个 SKU 调价或换渠道。
- 毛利底线：综合真实毛利 ≥ 10%。连续 2 周以下 = S2 事件。
- top-3 的 COGS > 售价 45% = 调价 + 谈判并行。
- 单订单运费亏损 ≥ 20% = `adjustShipping`（重称、换小箱、包进售价）。
- 凭记忆说出费率，误差 1 个点以内（第 4 天 drill）。

## 12. 故障排查（症状 → 原因 → 修法）

| 症状 | 可能原因 | 修法 |
|---|---|---|
| 利润偏高 | 缺供应商发票 → COGS 少算 | 把发票 `.txt`/照片丢进文件夹 |
| 利润偏低 | 发票重复（`.jpg` + `.jpg.txt` + `.txt`） | 自动去重；看 `files_ingested` vs `files_seen` |
| `reorder.csv` 为空但货架空了 | 名字不一致（`Tote` vs `Tote Bag Handmade`） | 改成一致；完全同名最保险 |
| 回复队列为空但仍有投诉 | DM 是截图不是文本 | 导出 `.txt`/`.json` 或粘进 `instagram_dm.txt` |
| 费率不对 | 文件名误判渠道 | 命名 `shopify_*`、`etsy_*`、`amazon_*` |
| `;` 的 CSV 被忽略 | 本地导出（`;` 分隔） | 已支持——Sniffer 会处理；检查 UTF-8 |
| 乱码（`ï»¿`） | Excel 的 BOM 头 | 已支持（`UTF-8-SIG`） |
| 某文件 0 行 | 编码 / 无表头 | 按 UTF-8 打开，确认表头行 |
